# Domain Context: Fintech (金融科技)

> 行业背景知识库，供 PM 在需求定义过程中参考。此文件内容不绑定到具体产品逻辑，而是行业通用知识。

---

## 一、行业概述

### 主要业务模式

| 模式 | 说明 | 典型玩家 |
|------|------|---------|
| **助贷** | 平台方利用自身流量和技术能力帮助用户向持牌金融机构申请贷款，平台不直接放贷 | 360借条、乐信、信也 |
| **联合贷** | 平台与持牌金融机构按比例共同出资放贷，共担风险 | 微众银行、网商贷 |
| **导流** | 平台将用户流量引导至持牌金融机构，由机构完成风控和放款 | 今日头条、美团 |
| **纯线上信贷** | 全流程线上化的个人消费信贷/现金贷 | 借呗、微粒贷、京东金条 |
| **分期电商** | 用户在平台购物时选择分期付款 | 花呗、京东白条 |

### 行业角色

- **资金方 (Capital Side / 资方)** — 提供放贷资金的持牌金融机构（银行、消金、信托）
- **平台方 (Platform)** — 连接用户和资金方的技术服务方
- **增信方** — 提供担保/保险服务的机构
- **征信机构** — 央行征信、百行征信、朴道征信等

## 二、监管框架

### 核心法规

| 法规 | 核心要求 | 对产品的影响 |
|------|---------|------------|
| **商业银行互联网贷款管理办法** | 互联网贷款需遵循独立风控、资金用途监控、合作机构准入等要求 | 风控流程设计、合作机构展示 |
| **金规〔2026〕2号 综合融资成本明示** | 要求向借款人明示综合融资成本（IRR/APR），包括利息+费用 | 费用展示、强制阅读、借款确认页设计 |
| **金融产品网络营销管理办法（八部委）** | 金融产品营销需合规，禁止诱导性宣传 | 营销文案、转化流程设计 |
| **个人信息保护法** | 个人信息收集需告知+同意，最小必要原则 | 授权协议、数据采集设计 |
| **消费者权益保护相关法规** | 保障借款人知情权、自主选择权、公平交易权 | 还款提醒、逾期处理、客诉机制 |
| **断直连/支付监管** | 支付渠道需多元化，不依赖单一通道 | 还款渠道设计、绑卡策略 |

### 合规红线

- **利率上限**：IRR 不超过 24%（部分场景 36%），APR 需明示
- **强制阅读**：关键费用/条款需用户确认阅读后才能继续
- **征信授权**：查征信/上报征信需单独授权，不能捆绑同意
- **催收合规**：催收时段、频次、方式有明确限制
- **数据安全**：用户敏感信息（身份证、银行卡）需加密存储传输

### 监管趋势

- 综合融资成本透明化（所有费用统一口径展示）
- 消费者保护升级（还款保障、知情权）
- 数据治理趋严（个人信息保护专项检查）
- 支付渠道多元化（不依赖单一支付通道）

## 三、核心术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 年化利率 | APR / IRR | 综合融资成本的年化表达，APR ≈ IRR×12（近似） |
| 资金路由 | Capital Routing | 根据规则将借款请求分配给最优资方 |
| 通过率 | Pass Rate | 风控审核通过的用户比例 |
| 放款成功率 | Disbursement Rate | 审核通过后成功放款的比例 |
| 绑卡 | Bind Card | 用户绑定银行卡用于借款/还款 |
| 代扣 | Auto-Debit | 系统自动从绑定银行卡扣款 |
| 还款渠道 | Repayment Channel | 用户主动还款的方式（微信、支付宝、银行卡等） |
| 逾期 | Overdue / Delinquency | 到期未还款，按逾期天数分级（M0/M1/M2...） |
| 催收 | Collection | 对逾期用户进行催缴 |
| 资方 | Capital Partner | 提供放贷资金的金融机构 |
| 增信 | Credit Enhancement | 通过担保/保险等方式提升信用等级 |
| 强制阅读 | Mandatory Reading | 用户必须阅读并确认某些内容才能继续操作 |
| 灰度 | Gray Release / A/B Test | 对部分用户开放新功能进行实验 |
| Nacos | Nacos | 配置中心，常用于管理业务开关、阈值等 |

### 逾期阶段

| 阶段 | 天数范围 | 说明 |
|------|---------|------|
| M0 | 1-30天 | 早期逾期，短信提醒为主 |
| M1 | 31-60天 | 电话催收 |
| M2 | 61-90天 | 高强度催收 |
| M3+ | 91天+ | 可能委外催收或法律途径 |

## 四、常见产品模块

### 借款模块
- 借款申请流程（额度申请→审批→签约→放款）
- 额度管理（总授信、可用额度、恢复规则）
- 借款页面设计（金额选择、期限选择、费用展示）

### 还款模块
- 主动还款（绑定卡还款、微信/支付宝、转账）
- 自动代扣（签约代扣、扣款顺序、重试策略）
- 提前还款（部分/全部、费用计算）
- 还款计划展示（每期金额、日期、状态）

### 绑卡模块
- 绑卡流程（四要素验证、银行卡鉴权）
- 绑卡策略（主卡/备选卡、绑卡上限）
- 解绑/换卡流程

### 费用模块
- 费用项定义（利息、服务费、担保费、保险费...）
- 费用展示规则（统一口径 vs 分项展示）
- 费用优惠/减免

### 风控模块
- 反欺诈规则
- 信用评分
- 额度审批
- 交易监控

## 六、产品设计常见维度

在 fintech PRD 中，以下维度几乎每次都要考虑：

| 维度 | 典型问题 |
|------|---------|
| **判断节点** | 这个检查在前端还是服务端做？ |
| **开关/灰度** | 全局开关还是逐维度？配置中心还是代码？热加载？ |
| **实验 vs 合规** | 这是合规红线（所有组必须遵守）还是实验变量？ |
| **阻断行为** | 不通过时怎么提示？Toast/Popup/Button禁用？文案可配？ |
| **白名单** | 测试UID白名单？资方过渡期白名单？共享还是独立？ |
| **告警** | 实时告警还是小时汇总？阈值升级？事件日志表？ |
| **错误处理** | 配置API超时/异常时怎么办？暂停倒计时？阻断借款？ |
| **数据埋点** | 哪些事件需要上报？维度有哪些？BI报表如何设计？ |
