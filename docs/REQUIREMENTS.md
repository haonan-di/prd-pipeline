## 一、定位与价值主张

### 1.1 一句话

> **一个开源、中文优先的「AI 产品经理副手」**——把 agent 编排成一个会做 PRD 的产品经理（方法论 + 可插拔的领域知识），并把整条链路串起来：**调研 → 结构化讨论 → 生成 → 审查 → 交付**。

### 1.2 它不是什么（防走偏）

- **不是**文档连接器：我们不持有任何平台凭证、不实现任何平台 API。在线文档系统靠**协同**用户已配置的文档 MCP 完成——我们负责"知道用户用什么、产出标准产物、给出交接与检索策略"。
- **不是** fintech 专用：fintech 只是内置的**一个精样板**，内核与领域解耦。
- **不是**模板填充器：核心是「逼着 PM 把需求想清楚」的过程，模板只是最后一公里。
- **不与**作者本机的私有 prd-workflow skill 合并。

### 1.3 差异化的落点

1. **拷问式澄清**——不接受第一版模糊表述，用带推荐答案的探针把需求逼到可判定、可执行、可测试；
2. **知识可插拔**——领域 / 人设 / 模板 / 合规 / 阶段 / 图表引擎都是文件，跟仓库走、可 diff、可被社区贡献；
3. **链路不断**——调研到交付是被打通的闭环；
4. **合规审查依据源**——同类产品的空白，可被用户/公司沉淀成自有资产；
5. **文档系统协同**——声明一次，历史调研与交付复用同一份认知，比人工翻文档高效。

## 二、目标用户与典型场景

| 用户 | 场景 | 诉求 |
|------|------|------|
| 开源使用者（首要） | 第一次用 | 不读源码、不看文档，被 agent 引导完成配置，直接开写 |
| 开源使用者 | 日常写 / 迭代 PRD | 一次对话内：调研 → 讨论 → 生成 → 审查 → 交付 |
| 开源使用者 | 已有自己的文档系统 | 声明所用系统/MCP 后，历史调研与交付都自动用上它 |
| 领域/合规贡献者 | 贡献行业知识、公司合规条款、自定义流程 | 自定义目录可扩展、可覆盖内置，机制清晰、维护方便 |
| 作者本人 | 真实工作（fintech PRD） | fintech 精样板的第一验证者（dogfood，**非产品设计约束**） |

**语言**：中文优先；结构与文件命名预留双语（D4，英文文案进 backlog）。

## 三、产品形态与边界

### 3.1 形态（D1 已拍板）

**薄 MCP server（确定性内核）+ SKILL 编排**。

```
Agent 编排层   —— SKILL.md：引导、讨论协议、审查协议、调研策略、交付确认（写在 markdown，无状态）
确定性内核     —— MCP server：预设扫描、模板渲染、校验、状态落盘、图表编码/渲染、本地写文件
知识层         —— presets：领域 / 人设 / 模板 / 合规 / 阶段 / 图表引擎（纯文件）
```

选择理由：作者已选定「只内置本地交付 + 关键状态全落盘 + 可扩展目录」，三者都要求**读写文件系统 + 确定性逻辑**；交给自己写的薄 server 可保证跨 MCP 客户端契约统一、模板渲染与校验不靠 agent 自觉。**不绑平台**这一条由"协同"策略保证，与形态无关。

### 3.2 边界（明确不做）

- 不做在线文档平台连接器（不实现 Confluence/飞书/Notion API，不存凭证）——**协同**用户的文档 MCP；
- 不做前端界面（工作台）——远期愿景，本期不实现，但状态落盘为其预留；
- 不做设计工具（Figma/MasterGo）集成；
- 不做多人协作 / 评审流 / 权限。

## 四、核心能力清单

> 归属标注：`编排` = 写在 SKILL.md；`内核` = 需要确定性内核（工具）；`知识` = 纯 preset 文件。

### A. 工作区

| # | 能力 | 行为 | 归属 |
|---|------|------|------|

| A2 | 状态自检 | 返回 `ready / uninitialized / draft` + 配置摘要；**静默自检，不是对用户的提问** | 内核 |
| A3 | 配置更新 | 查看/修改单项配置（用户显式触发）；支持后期补声明文档 MCP | 内核 |

### B. 知识（预设）

| # | 能力 | 行为 | 归属 |
|---|------|------|------|
| B1 | 预设发现 | 扫描**内置 + 自定义**目录，列出可用：领域 / 人设 / 模板 / 合规 / 阶段集 / 图表引擎；同名自定义**覆盖**内置并标注来源 | 内核 |
| B2 | 预设读取 | 按名读取单个预设全文 | 内核 |
| B3 | 预设校验 | 校验自定义预设的结构合法性（阶段集字段、图表引擎声明、合规章节），返回具体错误 | 内核 |

### C. 调研

| # | 能力 | 行为 | 归属 |
|---|------|------|------|
| C1 | 本地文档搜索 | 在配置的本地目录检索历史 md（标题 / 摘要 / 路径） | 内核 |
| C2 | **历史文档协同调研** | 依据 config 中声明的文档系统，产出**检索策略**（关键词 / 类 CQL 提示 / 空间范围），由 agent 调用用户的文档 MCP 检索**需求文档 + 技术文档 + 历史 PRD**，再综合成调研摘要（带引用） | 编排 + 内核 |
| C3 | 外部资料调研 | 竞品 / 行业实践的 web 检索**由 agent 完成**（尽力而为，内网禁外网时跳过并告知） | 编排 |

> C2 是「声明文档系统」的第一层红利：让 agent 能主动检索历史上下文，比让用户自己翻文档高效得多。

|---|------|------|------|

#### 4.1 图表管道：引擎可插拔 + 渲染策略消解外发风险（D3）

**分层**：

```
Agent（按图表规范撰写图源码）                    ← 生成职责在 agent（LLM 写 mermaid 强于正则解析）
    ↓ engine + code + placement
图表管道 —— 引擎无关：校验 → 编码/渲染（按引擎）→ 落源文件 → 返回交付物
    ↓
引擎注册表：
  ├─ 内置代码适配器：mermaid（默认）、drawio
  └─ 声明式引擎（预设声明，用户无需写代码即可新增）：
       源码格式 + 编码/渲染模板 + 支持的渲染策略
       例：plantuml / kroki / d2 / graphviz…
```

**渲染策略（引擎的属性，不是全局开关）**：

| 策略 | 含义 | 外发 | 典型场景 |
|------|------|:----:|---------|
| `source` | 只出源码，交目标平台或用户本地工具渲染 | 无 | Obsidian / GitHub / 聊天原生渲染 mermaid |
| `local` | 本地渲染成图（如 drawio CLI 导出 `.drawio.png`、本地渲染 mermaid） | 无 | 需要图片但涉密 |
| `remote` | 第三方渲染服务（如 mermaid.ink） | **有** | 便捷出图、非敏感内容 |
| `ask` | 用 `remote` 前逐图征求确认（**默认**） | 受控 | 一般默认档 |

**这就把「mermaid.ink 外发」从风险开关升级为机制**：默认 `source`（多数目标原生渲染，零外发）；需要图片时优先 `local`；`remote` 需确认。**drawio / html 的价值正在于提供 `local` 路径 + 二次编辑能力**：

- **drawio**：生成 `.drawio` XML 源 + 本地导出 `.drawio.png`（内嵌 XML，平台可见又可拖回编辑）——同时满足"平台兼容""二次编辑""零外发"；
- **html 原型**：生成高保真 HTML 线框，浏览器本地零依赖预览、本地截图嵌入 PRD；二次编辑经导入链路（Figma html.to.design / MasterGo html-to-mastergo）。

**图类型选择矩阵（SKILL.md 编排规范）**：

| 表达内容 | 图类型 | 引擎 | 备注 |
|----------|--------|------|------|
| 业务流程 / 判断分支 | flowchart | mermaid（默认）/ drawio（精修） | — |
| 系统间交互 / 时序 | sequence | mermaid | — |
| 页面/状态流转 | state | mermaid | — |
| 方案对比 / 结构梳理 | mindmap | mermaid | — |
| 排期节奏 | gantt | mermaid | — |
| 复杂架构 / 网络拓扑 | — | drawio | 分阶段落地 |
| 界面原型 / 线框图 | — | html | 分阶段落地 |

**引擎自定义（对应作者诉求"固化在预设里"）**：`presets/diagrams/` 声明启用/自定义的引擎与选项（源码格式、渲染策略、主题）。**声明式引擎**让用户不写代码即可接入新工具；复杂引擎（drawio）走代码适配器，社区可按接口扩展。

## 五、关键流程

### 5.1 初始化（引导式）

```
agent 静默自检状态
  ├─ ready          → 直接进入任务，不打扰
  ├─ uninitialized  → 逐项引导：文档系统声明(可跳过) → 预设 → 自定义目录 → 交付模式 → 写 config
  └─ draft          → 展示待补项，续起
```

要点：**用户唯一的手动入口是「显式要求改配置」**；除此之外不周期性询问。文档系统声明**可跳过**（不声明则仅本地交付，仍可用）。

### 5.2 主流程

```
调研(本地搜索 C1 + 历史文档协同 C2 + 外部检索 C3)
  → 讨论(阶段集循环：探针 → 用户回答 → 含糊则追问 → 结论落盘)
  → 生成(图表按引擎与渲染策略出图 + 模板渲染，落盘)
  → 审查(确定性检查 F1 + 合规依据源驱动的语义清单 F2，问题分级) → 用户确认定稿
  → 交付(默认 local_first：落本地 → review → 同步至声明系统；确认卡带默认值)
```

要点：
- **合规红线 / 事实性错误：发现即打断**（不等审查阶段）；
- 结构 / 清晰度问题：**通篇审查后一次性分级反馈**；
- 交付前一次**确认卡**（默认值来自 config），不构成周期性打扰。

## 六、扩展机制（可维护性是一等公民）

```
presets/                      ← 内置（跟仓库走，可 diff、可被社区 PR）
├── domains/      领域知识（行业背景、术语、红线）
├── souls/        岗位人设（思维方式、方法论）
├── templates/    PRD 模板
├── compliance/   合规审查依据源（按 产品形态 × 领域 × 辖区 组织；用户可增补自有条款）
├── stages/       讨论阶段集（含 _template 与字段说明，便于自定义）
└── diagrams/     图表引擎声明（启用/自定义引擎与选项）
自定义目录（config.preset_dirs）  ← 用户/社区扩展，结构同上，同名覆盖内置
```

**维护体验要求**（对应作者诉求）：

1. 每类预设都有 **`_template` 样板 + 字段说明**，照抄即可写自己的；
2. **B3 预设校验**给出具体错误（缺字段 / 枚举非法 / 引用不存在），不让人猜；
3. 覆盖规则统一：**同名自定义覆盖内置**，发现结果标注来源（内置 / 自定义 + 路径）；
4. 合规依据源**独立可沉淀**：公司可把自己的合规政策作为自定义文件放入，被审查环节自动叠加。

## 七、数据与配置结构

### 7.1 工作区状态与交付落点（三处别混）

**三个位置、三种职责**（D5 的核心，澄清"状态根"到底指什么）：

1. **工作区根 `workspace_root`**——一个**容器目录**。**默认按「项目」派生**：由 agent 依据会话的项目目录确定后传入 init（服务器 cwd 作兜底）——**无需用户手输**，契合 harness 的「session ↔ project ↔ 文件夹」模型。每个 PRD 任务在其下开一个 **`<slug>/` 子目录**（即"一个需求一个文件夹"），因此**不同需求不会混**。可通过 config 覆盖为任意位置（例如集中到用户目录）。
   - **变体（手动绑定）**：若会话工作目录**本身就是一个需求目录**（含 `state.yaml` 标记），则优先按它——用户主动进入即等价于"一需求一文件夹"。见 §7.3。
2. **任务目录 `workspace_root/<slug>/`**——该需求的全部工作状态与版本，是**单一状态源**（为未来工作台预留）：

```
<workspace_root>/<slug>/
├── state.yaml              阶段进度、当前版本、就绪状态
├── discussion-<stage>.md   每阶段讨论结论
├── prd-v<版本>.md          各版本 PRD 成品
└── assets/                 图源文件（drawio / html 等）
```

3. **交付落点**——最终 PRD 的去处，由 `document_system` 决定：`local` → `vault_path/subdir`；`remote` → 声明的文档系统。**交付落点与工作区根解耦**（可相同可不同）。

### 7.3 需求定位规则（合成：自动绑定 + 尊重手动）

**一个需求一个文件夹**（两种绑定方式共有）。**绑定顺序**（agent 按序执行）：

1. **会话工作目录本身已是需求目录**（含 `state.yaml`）→ 直接用它。这是"手动绑定"（用户主动进入需求文件夹）——确定性最强，白送；
2. 否则在 `<项目>/.prd/` 下定位需求 slug：
   - 对话里点了名 → 匹配或新建，**不问**；
   - 没点名但存在活跃需求 → 提议续用，**一句确认**；
   - 仍不确定 → 列出该项目下的 slug **+ 一个「新建需求」选项**（因可能存在任一现有需求都不是的情况），**选一次**；
3. 用户选择「新建需求」→ 新建 slug。

**要点**：根**不询问**（由项目目录派生或按已进入的需求目录）；"问"**至多一次**，且只发生在开场无法判断时；用户开场说清给谁写 → **零追问**。默认自动绑定之所以优于"每次手动切目录"，是因为它在所有 harness（含桌面聊天客户端）上都成立，且省去"建目录→切进去→再开口"的仪式。

### 7.2 config（草案 schema）

```yaml
version: 3
status: active               # active | draft
workspace:
  domain: fintech
  product_form: c-end        # c-end | b-end（联动合规依据源）
  soul: c-end-pm
  template: standard
  stages: standard           # 阶段集预设名
document_system:
  type: local                # local | confluence | feishu | notion | other
  mode: local_first          # local_first（默认，先落本地 review 后同步）| remote_first
  local:
    vault_path: ""
    subdir: PRD
  remote:                    # 仅用于协同；不含凭证（凭证由用户的文档 MCP 持有）
    platform: confluence
    mcp_server: ""           # 用户声明的文档 MCP 名（后期可补）
    space: ""
    parent_page_id: ""
    sync_note: ""            # 交接/同步指引补充
diagram:
  default_engine: mermaid
  render: ask                # source | local | ask | remote
  engines: []                # 额外启用/自定义引擎（来自 presets/diagrams）
preset_dirs: []
workspace_root: ""           # 工作区根：空=由 agent 按会话项目目录派生（<项目>/.prd）；可覆盖为任意路径
search:
  recent_keywords: []
```

> **迁移**：`readConfig` 检测旧版本（v1/v2）→ 内存迁移补默认值 → 按需回写，不丢用户数据。
> **凭证**：v3 **不存任何在线平台凭证**——这是「不内置连接器、只做协同」的直接红利。

## 八、质量与验收标准

### 8.1 测试策略

| 层级 | 范围 | 方法 |
|------|------|------|
| 单元 | 模板渲染契约、占位符检出、图表编码、预设扫描与覆盖、预设校验、config 迁移 | 纯函数直测 |
| 集成 | 全链路 stdio 冒烟（初始化 → 讨论落盘 → 生成 → 审查 → 本地交付） | 入仓冒烟脚本 |
| 验收 | 真实本地目录走查 | 人工 |

### 8.2 验收标准（改造完成定义）

1. **AC1 初始化**：全新环境 → 配置 → init 引导完成，全程不读源码；**不声明文档系统也可就绪**（仅本地交付）。
2. **AC2 端到端**：一次对话走完 调研 → 讨论（阶段集 + 结论落盘）→ 生成（**产物无残留占位符**、图按策略可渲染）→ 双层审查 → 交付。默认 `local_first` 落本地；声明了文档系统时给出同步交接指引。
3. **AC3 扩展**：自定义预设（含**阶段集 / 图表引擎 / 合规条款**）能被发现、能覆盖内置、来源标注正确、校验报错清晰。
4. **AC4 图表**：引擎可插拔生效——默认 mermaid；新增一个**声明式引擎**（预设文件即可）能跑通；`source` / `local` 路径不产生外发。
5. **AC5 单测**：上述单元 + 集成测试通过；冒烟脚本入仓。
6. **AC6 文档**：README 与 `SKILL.md` 与新定位一致（**彻底移除 wiki-mcp 依赖叙事**）。

### 8.3 如何验证与回归（回应「不知道如何回归」）

**测试金字塔**——L1–L4 无外部依赖、CI 可跑；L5 人工：

| 层 | 内容 | 何时跑 | 外部依赖 |
|----|------|--------|:--------:|
| L1 契约 | zod schema 校验：config / 六类预设 / 工具 I/O | 每次改动 | 无 |
| L2 单元 | 纯函数：模板渲染、占位符检出、ink 编码、预设扫描/覆盖、config 迁移 | 每次改动 | 无 |
| L3 集成冒烟 | 脚本驱动 stdio 全链路（init→…→publish local），断言结构化输出 | 每次改动 | 无 |
| L4 快照 | 固定 模板 + sections + 讨论 → 生成 PRD 必须等于入库期望文件 | 每次改动 | 无 |
| L5 人工 | 真实本地目录 / 真实文档 MCP | 里程碑末 | 有 |

**回归方式**：`npm test` 覆盖 L1–L4、`npm run smoke` 覆盖 L3；L5 按里程碑人工走查。**每个里程碑落地即补对应测试；后一个里程碑的回归 = 跑全部既有测试 + 本里程碑新增**。这样"花括号没被替换"这类契约 bug 一旦回归，会被 L4 快照立刻抓住。

## 九、里程碑（契约先行 / 逐段可验证 / 尽量不返工）

> 回应作者两问：
> - **尽量不返工** → **先冻结契约，再填实现**。所有互相牵连的接口（config / 预设 / 模板占位符 / 工具 I/O / 状态布局 / 图表引擎）在 **M0 一次性定死**；之后每个里程碑只在冻结契约上填充，不推倒重来。
> - **尽量可验证** → 每个里程碑都附可跑的验证点，回归 = 累积跑全部既有测试（见 §8.3）。

| 里程碑 | 交付 | 验证点（可回归） |
|--------|------|-----------------|
| **M0 契约冻结**（先做） | `types.ts` 重写为 zod schema（config v3 / 六类预设 / 工具 I/O / 状态布局 / 引擎接口）+ 模板占位符规范 + `docs/CONTRACTS.md` | L1 契约用例通过；编译通过 |
| **M1 骨架修复** | 模板渲染按契约、本地交付走 config、预设扫描、图表编码修正 + mermaid 引擎注册表 | L4 快照（产物无残留占位符）、ink 编码已知向量、L3 冒烟（init→generate→publish local） |
| **M2 状态与讨论内核** | 状态落盘、阶段集驱动讨论 + 探针选项、预设校验、确定性审查 | 落盘结构断言、阶段集渲染快照、校验用例、review.check 用例 |
| **M3 知识层** | presets 六类重构 + 自定义目录覆盖 + 合规依据源 + `_template`/文档 | 扫描/覆盖/校验用例、合规叠加快照 |
| **M4 文档系统协同** | init 声明、历史调研策略、local-first 同步交接指引 | config 落盘断言、检索策略快照、交接指引快照 |
| **M5 图表工具链** | drawio 适配器（本地导出）、html 原型适配器、声明式引擎 | 声明式引擎接入用例、local 出图路径用例 |
| **M6 编排重写** | `SKILL.md` 按新流程重写（grill-me 协议、审查协议、调研策略、交付确认卡） | 人工走查 checklist |
| **M7 验收** | AC1–AC6 全量走查 | 真实环境人工 + 全量回归 |

**滚动交付**：每完成一个里程碑即停下 review，并跑全部既有测试；不追求一次做完。
**建议节奏**：先做 **M0 → M1**——把"跑不通"变成"跑得通、且契约锁死"，停下 review 再定后续深度。

- backlog：双语 / 工作台 / npm 发布 / 更多领域与引擎。
